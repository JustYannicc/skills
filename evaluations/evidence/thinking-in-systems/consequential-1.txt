## Governing assessment

This is a **material change to an existing Durable System**: it changes a standing classification rule, affects future intake and existing cases, and creates a legacy transition obligation.

The intended Outcome appears to be one consistent classification rule across the case population. Before any effect, the change needs an accepted successor System contract and a linked change-and-legacy record. The `'Workflow'` skill should coordinate that work; this assessment does not select its phases or apply the rule.

### Decision boundary

Proposed scope:

- New cases from the cutover date.
- Existing cases created under the old rule.
- Historical classification, audit, reporting, downstream decisions, and any interfaces or people that consume classifications.

Not yet authorized:

- Reclassifying any case.
- Overwriting original classifications or history.
- Changing downstream decisions retroactively.
- Treating the new rule as if it had always governed prior cases.
- Activating the successor rule without the responsible authority’s approval.

### Material gaps to resolve

The smallest questions that can materially change the safe transition are:

1. What is the new rule’s exact, versioned definition and effective date?
2. Which authority approves the rule, the legacy disposition, and any downstream effects?
3. What depends on the current classification—eligibility, routing, reports, permissions, notices, contracts, or external commitments?
4. For existing cases, does the new classification change only a current label, or also prior/current decisions and obligations?
5. What authoritative case record holds the original rule version, original classification, and later reclassification history?
6. What evidence proves the new rule is correct across normal, ambiguous, invalid, and legacy cases?

### Proposed legacy disposition

Do not use a single blanket “replace every case” operation. Classify every discoverable case cohort before any live change:

| Cohort | Proposed disposition |
|---|---|
| Unaffected | Preserve unchanged, with the reason recorded. |
| Compatible | Keep the existing classification; bind it to the prior rule version. |
| Auto-adapt | Reclassify through a deterministic, simulated transformation where equivalence is proven; retain old value, old rule version, new value, new rule version, timestamp, and reason. |
| Review-required | Queue for accountable human decision where ambiguity, incomplete inputs, or consequential downstream effects prevent safe automatic reclassification. |
| Conflict | Preserve current state and block automatic change where old and new classifications imply incompatible rights, commitments, or effects. Escalate using a defined resolution authority. |
| Exempt | Preserve under an explicit approved exemption and review condition. |
| Unreachable/unknown | Do not claim coverage. Preserve the gap, prevent misleading completion claims, and define discovery/reconciliation and a recheck trigger. |

Historical facts must remain intact. A new rule may govern a current or future decision, but it must not rewrite history to imply the new rule always applied.

### Required governing constraints

- One writable authority owns case classification; reports, dashboards, exports, and indexes are derived views that identify source revision and freshness.
- The successor rule has a stable version and explicit applicability: which cases, conditions, and dates it governs.
- Simulation uses the intended production path, produces exact proposed case changes and downstream effects, and does not write live durable state.
- Approval binds the exact rule version, cohort rules, assumptions, and simulation result.
- Cutover has defined scope, rollback or repair behavior, reconciliation, and visible proof.
- A degraded path exists: if classification inputs, authority, dependencies, or proof are unavailable, preserve state and pause effects rather than silently guessing.
- The System measures both correctness and burden: classification accuracy/consistency, affected-case coverage, exceptions/conflicts, downstream errors, review load, delay, and harmful reversals.

### Proportionate proof before activation

At minimum, prove:

- New intake is classified by the new rule only after the effective boundary.
- Each legacy cohort receives its declared disposition.
- Ambiguous and conflicting cases do not auto-transition.
- Original captures and prior decisions remain inspectable.
- A simulated transition matches the approved exact proposal.
- Rollback/repair can restore the accepted prior operational state without erasing history.
- Reconciliation identifies cases missed, duplicated, or classified under an inapplicable rule version.

The governing recommendation is therefore: **prepare a versioned successor rule and a cohort-based legacy plan; simulate and approve the exact transition; then hand the bounded constraints and proof obligations to `'Workflow'` for coordination.**
